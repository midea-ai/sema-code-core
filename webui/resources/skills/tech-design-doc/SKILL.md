# 技术文档写作

目标读者：懂领域、不懂本项目的人。他们要看懂的是**设计意图**，不是代码走读。

## 流程

1. **先读透代码**，把机制的入口、分支、降级路径、事件出口、状态副作用全部列出来，再动笔。
2. **先出大纲，等确认**。大纲不超过 10 行，一级章节不超过 5 个。用户确认后再展开全文。
3. **写完自检**（见文末清单），再交付。
4. 用户会逐段挑不重要的内容让删，交付后按要求精简，不要辩解。

## 组织原则

- **以读者的问题为线索**：这是什么、为什么这样设计、怎么用、出问题怎么办。禁止按时间顺序或文件目录叙述，禁止"第一步做了什么、第二步做了什么"。
- **开头要让外人听懂**：第一段用人话说这是什么东西、给谁用，紧跟一个具体的使用例子（"用户说 X，它就……"），再讲为什么这样设计。项目内部术语（宿主应用、内核、某某层）第一次出现必须先解释，不能一上来就"能力以宿主无关的方式暴露"这种只有项目成员懂的话。
- **逐步披露**：第一章只给问题定义、取舍、一张全局图、一张各级/各模块的对比表。数字门槛、规则细节、措辞全部下沉到后面章节。
- **章节开头的总述要带观点，不是报目录**。可以写一两句让读者知道这一章的主线（"越靠前的层越根治，越靠后的越像补丁"），也可以不写；禁止"这一章回答三个问题：……后面各章是对结论的展开"这类流水账式导读。每个子章节第一段先总结再细讲，不要一上来就是判据和规则。调研/对比类章节的每个小节，开头加一句**大白话结论**，用引用格式写成 `> **一句话：** ……`，外行能懂，最好带一个生活化或项目内的例子，再展开证据。只有存在取舍或对比（为什么选 A 不选 B）的小节才用；纯描述性小节（数据模型、接口清单、功能列表）不加，加了只会和首段重复，一份文档里出现两三处就够。
- **重要子主题拆成独立 md 文件**，主文档用一行指向它。
- **每一级标题下的同级子标题不超过 5 个**。超了就合并，往下开三级、四级（`####`）。同级之间有重有轻是正常的，不要为了齐整平铺 7、8、9 个小节。
- 标题格式：`## 一、标题`，`### 1.1 子标题`，三级以下不编号。

## 内容原则

- **"为什么"多于"是什么"**。每个关键设计（分层、数据模型、协议选择、阈值）写清：解决什么问题、考虑过哪些替代方案、为什么放弃、当前方案的已知代价。
- **方案选择必须先介绍每个候选方案是什么**（各一两句），再用表格按维度对比。读者看不懂的方案名等于没写。
- **代码 30 秒能看到的不写**：函数名、文件名、参数列表、调用链。只有读者必须去看的位置才点名，一句话最多一个。
- **用具体替代空词**：不用"强大""灵活""高效"，用数字、条件、例子。
- **不写渲染气氛的断言句**：像"任何一个没堵，其他的都白做""等于门锁了窗开着"这类强调语气的句子不要出现，只陈述事实、条件和要求。
- **不做防御性写作**：结论直接下，不预先替自己留退路。不写"结论不成立的条件""动手前需要确认""这是假设/推算，上线后再调整""这一项其实不构成差别""对方也能绕过去"这类自我限定和替对手方案找补的句子。对己方不利的事实留在对比表的单元格里，不另起段落解释它"影响有限"。已知代价集中写一处，每条一句。
- **解释点到为止**：一个事实配一句解释。某个坑或机制的原理能放进表格单元格，就不单独展开成段落或列表；排除某个方案的理由，只写对比表里放不下的那一句。
- **一个事实只在一处展开**：同一个结论在文首、章节总述、正文、文末反复出现时，只留一处完整表述，其他地方最多用一个短语指代。成对的重复结构合并成一个：特性表和标准列表合成一张表，文首结论和文末结论只留一个。
- **用场景开头**：重要主题用一个具体故障场景引入（"用户激活了 X，做到第三步时……"），再解释机制。
- **约束与陷阱就地写**：不能动的假设、容易踩的配置、性能边界、技术债，写在它所属的章节里，不单独开"陷阱"章。单独的陷阱章读者不知道它存在的意义。
- **规则背后的事故**：每条防御性规则写它防的是什么实际问题。
- **文档自包含**：不提及、不引用其他内部文档（本文拆出去的子主题文件除外），读者手里没有。需要的背景和结论直接写进本文。
- 文档语言与用户提问语言一致。对外文档不出现具体模型厂商的风格名等指涉。

## 形式原则

- **表格只用于多行 × 多属性的对比**（≥3 列，或 ≥4 行且每行多个属性）。两列短清单改项目符号，两行对比改一句话。表格滥用和不用一样差。
- **图用 mermaid，按需混用**：flowchart 画流程和降级链，sequenceDiagram 画消息/调用时序，stateDiagram-v2 画生命周期，classDiagram / erDiagram 画数据模型。一段流程配一张图，不要为了画而画。
- **一段不超过 4 句**，长了就拆或改成表。段落一个观点，句子直接。不用"接下来我们""值得一提的是"。
- **散文段不连续堆叠**。一个小节里连续两段以上的纯文字会让读者"看着头疼"：并列的规则、事故、步骤改项目符号（带粗体引导词），多属性的改表格，散文只留场景引入和观点总述。列表与表格之间用一句话承接。
- **同类产品对比给两张表**：一张"功能 × 产品"的对应表，一张"维度 × 产品"的特性对比表。前者读者拿来逐项核对，后者拿来做结论。对应表每格填对方的具体工具名或库方法名；对方用另一种形态实现（比如 MCP 工具 vs JS 库方法）时照样填方法名，只有确实没有这个功能才填"无"，一列大片"无"就是没查够。只体现工具形态、与功能无关的行（会话重置、模块路径之类）不要列。
- **列表平铺不超过 5 条**。超过 5 条说明该分组：多属性的改表格，有主次的改成带粗体引导词的叙事段，同类的合并成一句。大段大段的列表读起来像机器输出。
- 成本类表述要具体到计量单位（token、毫秒、调用次数），不写"不花钱"。

## 交付前自检

- [ ] 一级章节 ≤ 5，每级下的同级子标题 ≤ 5，章节总述带观点或不写，子章节先总结后细节
- [ ] 没有超过 5 条的平铺列表，没有超过 4 句的段落，没有连续两段以上的纯文字
- [ ] 每个关键设计都有替代方案和放弃原因
- [ ] 方案对比表前有每个方案的介绍
- [ ] 没有可以从代码 30 秒看出来的内容
- [ ] 没有过渡废话，没有空词
- [ ] 没有防御性表述：没有"结论不成立的条件""需要确认""这是假设"之类的自我限定，没有替不利事实辩解的段落
- [ ] 同一事实只展开一次，没有内容重叠的两张表或两个列表，解释的篇幅不超过它所解释的事实
- [ ] 表格都是多行多属性；短清单没有做成表
- [ ] 没有孤立的"陷阱/排查"章，约束都在所属章节里
- [ ] 标题能看出章节间的递进关系（问题 → 选型 → 实现 → 使用）
